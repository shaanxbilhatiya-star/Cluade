# Zero-dependency movie booking system with file-based JSON backend and single-file SPA frontend

A complete movie booking web app: Node.js HTTP server (726 lines) using only built-in modules and a 93KB single-file SPA (index.html) with 5 mobile-first screens matching the purple-themed design specs. The backend provides REST APIs for movies, showtimes, bookings, food items/orders, users, and stats, persisting everything as flat JSON files on disk. The frontend is a vanilla HTML/CSS/JS SPA with inline SVG icons, generated poster art, and a complete booking flow (movie → date → time → seats → form → confirmation). No external dependencies, no build step.

Watch for: Concurrent write race conditions on all JSON data files that will corrupt bookings under load (confirmed). No authentication or authorization on any endpoint—anyone can delete movies, cancel others' bookings, or overwrite user profiles (confirmed). XSS via innerHTML injection since movie creation is unauthenticated (confirmed). Hardcoded phone number `9876543210` used as the session identity for My Tickets, meaning all users share one booking stream (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The server reads and writes entire JSON files on every request with `readFileSync`/`writeFileSync`. Two requests arriving simultaneously can both read the same state, compute different mutations, and one write silently overwrites the other—losing bookings or double-selling seats. This is the most critical operational gap.

Every API endpoint is unauthenticated. The `/api/movies` POST/PUT/DELETE routes, `/api/bookings` DELETE, and `/api/users/:id` PUT are all publicly accessible. Since the system uses file-based persistence without any user session model, there's no natural place to graft auth later.

The frontend identifies the current user solely by the hardcoded phone number `9876543210` embedded in the `loadTickets()` fetch call. There's no login screen, no token, no session.

The body parser accumulates `chunk.toString()` into a string and only checks `body.length > 1048576` after concatenation. A single large chunk exceeding 1MB gets concatenated before the check fires, causing a memory spike before rejection.

All render functions insert server-returned strings directly into `innerHTML` without escaping. Combined with the unauthenticated movie creation endpoint, this is a stored XSS vector.

<details>
<summary>Issues (7)</summary>

1. **Race condition on JSON file writes** — Concurrent requests read-modify-write the same JSON files without locking. Use a per-file mutex or atomic rename pattern to prevent data loss.
2. **No authentication on any endpoint** — POST/PUT/DELETE on movies, bookings, users are all public. Add at minimum a shared secret or session token for write operations.
3. **Hardcoded phone number as session identity** — `loadTickets()` fetches bookings for `9876543210` with no login flow. Implement a basic session or at least persist the phone from the last booking.
4. **Body parser doesn't clean up on oversize** — When body exceeds 1MB, `reject` is called but the `data` listener isn't removed—subsequent chunks keep firing. The request stream should be destroyed.
5. **Synchronous file reads on every request** — `readFileSync` blocks the event loop. Under any concurrent load, response latency compounds. Switch to async reads or cache in memory.
6. **XSS via movie title injection** — `renderMovies()` and other render functions insert server-returned strings (titles, descriptions, cast) directly into `innerHTML` without escaping. A movie created with a title containing `<img onerror=...>` executes in all clients.
7. **Ticket tabs and filter pills are non-functional** — "Passed" and "Cancelled" tabs show an empty state instead of filtering by booking status. Filter pills (Movie, Food, Event) toggle CSS classes but don't filter content.

## File-based persistence and concurrent write corruption

The server calls `readJSON` (which uses `readFileSync`) then `writeJSON` (which uses `writeFileSync`) on every mutating request. There is no locking, no atomic write (rename pattern), and no in-memory cache. The race window: two simultaneous booking requests both read `showtimes.json`, both see seat A1 as available, both append A1 to `bookedSeats`, and the second write clobbers the first—double-selling the seat. The same pattern affects `bookings.json`, `movies.json`, and `food-orders.json`.

```javascript
// server.js lines ~12-29
function readJSON(filename) {
  const raw = fs.readFileSync(filepath, 'utf-8');
  return JSON.parse(raw);
}
function writeJSON(filename, data) {
  fs.writeFileSync(filepath, JSON.stringify(data, null, 2), 'utf-8');
}
```

The synchronous nature also means every request blocks the event loop during I/O. Under concurrent load, requests queue behind each other's file reads—a bottleneck that surfaces before the correctness issues do.

## Authentication and authorization gap

No endpoint checks identity. `DELETE /api/movies/:id` cascades to delete all associated showtimes. `DELETE /api/bookings/:id` cancels any booking and frees seats. `PUT /api/users/:id` lets anyone overwrite any user profile. `PUT /api/movies/:id` merges the request body via spread (`{ ...movies[index], ...body, id: params.id }`), allowing injection of arbitrary fields into the data store.

The only user identity is the hardcoded phone number baked into `loadTickets()`:

```javascript
const res = await fetch('/api/bookings?phone=9876543210');
```

## Body parser edge cases

The 1MB limit check happens inside the `data` event callback:

```javascript
req.on('data', chunk => {
  body += chunk.toString();
  if (body.length > 1048576) {
    reject(new Error('Request body too large'));
  }
});
```

`reject` is called but the `data` listener isn't removed—subsequent chunks keep firing and calling `reject` again on an already-rejected promise. The `end` event still fires afterward, calling `resolve` on an already-rejected promise (no-op). The memory spike from concatenation happens before the check triggers. The request stream should be `req.destroy()`'d on oversize to stop further accumulation.

## XSS via innerHTML

All render functions (`renderMovies`, `renderTickets`, `renderBookingDetail`, `renderFoodItems`) use template literals inserted via `.innerHTML`:

```javascript
document.getElementById('now-playing-list').innerHTML = nowPlaying.map(m => `
    <div class="movie-card" onclick="openBooking('${m.id}')">
        ...
        <div class="movie-title">${m.title}</div>
        ...
`).join('');
```

Since `/api/movies` POST has no auth, an attacker can create a movie with `title: "<img src=x onerror=alert(1)>"` and it executes in every client's browser. The same applies to `description`, `cast`, `cinema` names in showtimes, and user names. A simple `escapeHTML()` utility wrapping all interpolated server data would close this.

## Incomplete ticket filtering

The "Passed" and "Cancelled" tabs in `switchTicketTab()` render a static empty state:

```javascript
if (tab === 'upcoming') loadTickets();
else {
    document.getElementById('tickets-list').innerHTML = `<div class="empty-state">...No ${tab} tickets</div>`;
}
```

The data model supports filtering—bookings have a `status` field ('confirmed' or 'cancelled') and dates that could determine past vs upcoming—but the frontend doesn't filter on either dimension. The filter pills (Movie, Food, Event) toggle CSS active states but perform no data filtering.

## Booking cancellation doesn't cascade to food orders

`handleDeleteBooking` marks the booking as cancelled and removes seats from the showtime's `bookedSeats` array, but food orders linked via `bookingId` remain with `status: 'confirmed'`. If food order fulfillment is tracked separately, this creates an orphaned confirmed food order for a cancelled booking.
